# 源表重放终端

数仓值班工程师据原始分区和下游依赖复算回填范围，检查已有版本、输入缺失、迟滞依赖和预计行数。发布的是离线重放清单，页面上的写入与回滚均在样例快照上演练。

## 启动与演练

运行 `docker compose up --build -d`，访问 `http://127.0.0.1:18429/`。

1. 打开「华东夜班回填」。筛到「阻断」，点开分区查看缺失或过期的上游快照。
2. 切换「两分区演练」，点击「生成重放计划」。`orders` 与 `facts` 各增加 2 行，总行数 20 → 24。
3. 转到「回滚校验」。写入两项后，回滚摘要应与演练前摘要一致。相同清单再运行会复用批次。
4. 下载一份重放清单，包括上游版本、目标版本和前后校验摘要。

`POST /api/plans` 接收 `{"sample":"clean"}` 或表单的 `bundle` JSON 文件。模块及字段说明见 [深度登记](docs/DEPTH.md) 和 [数据字典](docs/DATA-DICTIONARY.md)。

## 凌晨迟到修订（续批）

下游已领走上一批重放计划后，迟到修订只能在原批之上续开，不整链重开：

1. 在任一原批页面切到「迟到续批」，表单自动带上当前原批编号；选择「凌晨迟到修订」或上传修订快照，点击「续开一批」。
2. 续批页给出三档：`可继续使用`（如 `orders@2026-11-17`，下游补数不中断）、`需要重做`（依赖新口径的分区）、`证据不足`（陈旧 previous 或缺上游快照，不进续批）。
3. 未处理的重复行进「重复留证」，冲突与无效行进「隔离留证」，源行号随证保留，均不混入处置档。
4. 同一份修订再次提交会复用同一份续批（200 + `reused`）；修订解析失败、规则漂移或目标行数矛盾时整单拒绝，原批记录与旧版指针不变。

接口为 `POST /api/continuation`（参数 `parent` 加 `sample` 或 `bundle`），查询 `GET /api/continuation/{id}`。续批不进版本签发的近期计划，也没有删除与批量运营入口。

运行 `docker compose exec -T app pytest -q` 复核。`docker compose down` 停止应用并保留批次历史。
